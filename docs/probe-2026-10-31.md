# Feasibility probe, 2026-10-31

Before building the experiment, the author ran a set of throwaway scripts on their own machine to find out whether an Agent SDK run behaves like a person running Claude Code, and what could leak between runs. The raw API request bodies were captured with Claude Code's `OTEL_LOG_RAW_API_BODIES` setting (with `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `OTEL_LOGS_EXPORTER=none`). Those bodies hold account and device identifiers, so they are not published; this note records what they showed.

## The system prompt

- **SDK and `claude -p` match.** With the same Claude Code build, the Agent SDK's `claude_code` system-prompt preset sends a system prompt identical to `claude -p`, apart from one per-request billing header line. Both begin "You are a Claude agent, built on Anthropic's Claude Agent SDK."
- **Interactive Claude Code differs.** The interactive terminal identifies itself as Claude Code, adds the `AskUserQuestion` tool, a tip about `!` shell commands and a note about ending conversations, describes the Bash and Agent tools differently, and included a section from a browser extension installed on the machine. None of these concerns notebooks or checking work, but they are differences, so the experiment states that it uses the non-interactive setup.
- **Versions matter.** The Claude Code build bundled in `claude-agent-sdk` 0.2.176 (2.1.316) differed by one system-prompt line from the separately installed 2.1.309, and the installed copy updated itself during the probe. The experiment therefore uses only the bundled build, pinned through the SDK version, with `DISABLE_AUTOUPDATER=1`.
- **Two prompt sizes.** Sonnet 5.5 received the shorter system prompt by default (about 6,900 characters); the full one is about 28,000. `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=1` pins the shorter one, so a change on the server side cannot switch it between runs.

## What leaks into a run

- **User settings.** By default the SDK loads user, project and local settings. On the author's machine that meant an installed plugin's start-up hook injected about 24,000 characters of instructions. With `setting_sources=["project"]` none were loaded.
- **Environment variables.** A run started from inside a Claude Code session inherited that session's variables, including its API base URL. The experiment starts every run in a fresh container with only the variables it needs.
- **The folder path.** The working folder's path appears in the system prompt. A folder named after the skill would tell the control side about it, so run folders have neutral names and sit outside this repository.
- **The rest of the machine.** An agent that could not find its data file searched the machine's temporary folder and the home directory. The experiment runs each side in its own container.
- **Account context.** Signed in with a plan, Claude Code added account context to the conversation (an email address and the global git user name). The containers have no git configuration; the system-prompt check before the pair records what remains, which is the same on both sides.

## Loading the skill

- The skill loads from a project's `.claude/skills/` folder, and also through the SDK's `plugins` option.
- Called by name (`/iterative-data-science` at the start of the prompt), the full SKILL.md text is in the first request to the model, before the model writes anything. This was checked twice, the second time with the bundled 2.1.316 build and Sonnet 5.5 at effort `high`.
- With a trivial prompt and no slash command, the skill was not loaded.

## A small end-to-end run

With the skill, a small notebook task on a synthetic temperature file took 11 turns, 58 seconds and an estimated $0.14. The agent executed the notebook with `jupyter nbconvert`, opened the saved PNG (the image reached the model), and caught a planted 999 °F value.

## The data

One probe week of Chicago taxi trips (not the week the experiment uses) downloaded twice through the portal's SODA API, ordered by `trip_id`, gave identical SHA-256 checksums. Each download took 100 to 250 seconds.
